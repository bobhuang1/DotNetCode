# Terraform: a large-scale Azure site

Infrastructure-as-code for a production-shaped web site on Azure: **Azure
Front Door Premium + WAF** in front, a **Premium v3 App Service** that
autoscales on CPU, **Azure SQL with a geo-replica and automatic failover**,
a **Premium Redis cache**, **Key Vault** for secrets, **Application Insights**
for monitoring, and **private endpoints** so SQL, Redis, and Key Vault are only
reachable from inside the VNet. App deployment is *not* part of the Terraform
state; the README shows how to wire it into CI/CD.

## What you get

| Component | File | Notes |
|---|---|---|
| Front Door Premium + WAF | `frontdoor.tf` | OWASP managed rules, bot rule set, geo custom rule, HTTPS-only route; origin reaches the app through its **private endpoint** |
| App Service (Premium v3, Linux) | `appservice.tf` | `dotnet` 10 stack, system-assigned identity, staging slot, VNet integration, CPU autoscale (1–5 workers) |
| Azure SQL geo-replica | `sql.tf` | Business Critical DB, secondary server in `location_secondary`, auto-failover group; the app connects to the **failover listener** |
| Redis (Premium) | `redis.tf` | Private-endpoint only, TLS |
| Key Vault | `keyvault.tf` | Private-endpoint only, RBAC; app identity granted `Key Vault Secrets User` |
| Monitoring | `monitoring.tf` | Log Analytics + Application Insights |
| Networking | `networking.tf` | VNet, app-integration subnet (delegated), shared private-endpoint subnet, private DNS zones, SQL listener DNS record |

## Run it

```powershell
az login
az account set --subscription "<your subscription>"

terraform init                      # see backend.tf.sample to use remote state
terraform plan -out plan.tfplan
terraform apply plan.tfplan
```

The `az` principal running the apply needs `Contributor` (or a scoped role)
on the subscription/Resource Group and the **Key Vault Administrator** data-
plane role to create the sample secrets (`azurerm_key_vault_secret`) with RBAC.

## Variables

`terraform.tfvars.sample` has runnable defaults (regions, SKUs, tags). Names
use `name_prefix`, `environment`, and a random suffix so the resource names are
unique. The SQL admin password is generated by `random_password`, which lives
in state — treat `terraform.tfstate` as a secret.

## Deploying the app (CI/CD, not Terraform)

Infra ends where the app begins. `outputs.tf` publishes what the pipeline needs:

- deploy to the **staging slot** via
  `az webapp deploy --resource-group rg-... --name app-... --slot staging --type zip --src-path publish.zip`
- smoke-test `staging`, then swap:
  `az webapp deployment slot swap --name app-... --resource-group rg-... --slot staging --target-slot production`
- `WEBSITE_RUN_FROM_PACKAGE = 1` is already set so the zip is extracted on the host.
- publish the .NET app with `dotnet publish -c Release -o ./publish`.
- `web_app_principal_id` lets the pipeline grant additional Azure roles (or
  the app itself) without hard-coding object IDs.

GitHub Actions and Azure DevOps both use essentially those commands; the app
endpoint is `outputs.front_door_endpoint`.

## Hardening notes for real prod

- Move to remote state (`backend.tf.sample`) before anyone else works on the repo.
- Add NSGs around the subnets, and follow the least-privilege zoning pattern:
  your platform may want separate endpoint subnets per service.
- Start the WAF in `Detection` mode, watch Application Insights, then flip to `Prevention`.
- Consider Entra-only authentication for Azure SQL instead of SQL admin + password.
- Scale to more regions by duplicating the App Service/Front Door per region
  and using `azurerm_traffic_manager_profile` or Global Front Door routing.
- `terraform destroy` removes everything this sample created; VNet peering or
  hardened data stores you build on top will need their own destroy lifecycle.

## Cost

This shape is expensive on purpose — Premium v3 workers, Business Critical SQL,
Premium Redis and Front Door Premium all bill continuously. For a node/mock
environment scale everything downward first (`terraform.tfvars`).
